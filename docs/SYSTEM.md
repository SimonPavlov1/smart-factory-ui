# Архитектура и производственный цикл

## Назначение

«Проекты» объединяет CRM и MES в одном интерфейсе. Система хранит производственные заявки, состав изделий, складские остатки, экземпляры с заводскими номерами и задачи сотрудников. Автоматические задачи создаются маршрутом производства, ручные — пользователями и не изменяют производственный маршрут.

## Компоненты системы

| Компонент | Технологии | Ответственность |
|---|---|---|
| Frontend | React 19, Vite, Tailwind/PostCSS | Интерфейс CRM, календарь, канбан, формы операций |
| Backend | FastAPI, SQLAlchemy, Pydantic | API, права, workflow, складские транзакции |
| База данных | SQLite локально, модели совместимы с PostgreSQL | Заказы, задачи, BOM, остатки, движения и экземпляры |
| Миграции | Alembic | Версионирование схемы |

Frontend обращается к `/api/*`. В локальной разработке Vite удаляет префикс `/api` и проксирует запрос на `http://127.0.0.1:8000`.

```text
Браузер
   │ /api/*
   ▼
Vite / nginx
   │
   ▼
FastAPI ── SQLAlchemy ── SQLite/PostgreSQL
```

## Производственный маршрут

Основная цепочка:

```text
Заявка
  → анализ BOM и резерва
  → закупка дефицита
  → оплата
  → приёмка компонентов
  → выдача и получение комплектующих
  → сборка
  → тестирование
      ├─ годно → упаковка
      └─ дефект → ремонт → повторное тестирование
  → оприходование готовой продукции
  → готово к отгрузке
```

Если в карточке изделия включено «Тестировать до сборки», после поступления материалов создаётся предсборочная проверка. Только прошедшие проверку экземпляры допускаются к сборке. После ремонта изделие возвращается в существующую задачу тестирования; закрытая накопительная задача переоткрывается для новой партии.

## Экземпляры и заводские номера

Каждое физическое изделие представлено записью `Item`. Заводской номер формируется из префикса изделия и последовательности `001`, `002`, `003` и далее. Дата в отображаемую часть номера не входит. Для изделия хранится также децимальный номер.

Типичные состояния экземпляра:

```text
planned → in_assembly → assembled/testing → passed
                                      └──→ repair
passed → packed → stocked
```

Переходы выполняются по конкретным экземплярам, поэтому результаты одного заводского номера не должны изменять другой.

## Накопительные задачи и партии

Тестирование, упаковка и оприходование могут выполняться частями. Для этого система использует одну накопительную задачу и несколько `WorkflowBatch`.

Правила:

- новая партия того же изделия добавляется в существующую задачу;
- завершённая задача переоткрывается при возврате изделия после ремонта или поступлении новой партии;
- параллельная ветка другого изделия не удерживает задачу открытой;
- обработанная партия не может быть оприходована повторно;
- заказ готов к отгрузке только после завершения всех веток и оприходования требуемого количества.

## Тестирование и ремонт

Тестировщик закрепляет за собой отдельные заводские номера. Несколько тестировщиков могут работать в одной задаче без пересечения.

Для каждого экземпляра заполняется собственный чек-лист:

- все пункты закрыты — экземпляр передаётся на упаковку;
- есть незакрытый пункт — экземпляр передаётся в ремонт;
- причины дефекта формируются из незакрытых пунктов и сохраняются отдельно по заводскому номеру.

После ремонта инженер описывает выполненные работы для каждого устройства. Затем устройство возвращается только на повторное тестирование.

## Склад

Склад различает:

- фактический остаток;
- зарезервированное количество;
- доступное количество;
- движения прихода, расхода и ручной корректировки.

Любое ручное изменение количества создаёт запись в истории движений. Оприходование готовой продукции защищено от повторной обработки одной и той же партии.

## Ручные задачи

Ручная задача может содержать:

- название и описание;
- отдел и исполнителя;
- приоритет;
- плановое начало и дедлайн;
- оценку времени;
- связь с заказом или изделием;
- наблюдателей;
- блокирующие зависимости.

Ручная задача отображается в общем календаре и канбане, но не создаёт автоматических производственных переходов.

## Отмена заявки

Отмена выполняется управляемо:

1. руководитель запрашивает отмену;
2. система анализирует резервы, выданные материалы, закупки и активные задачи;
3. создаются обязательства по возврату или урегулированию;
4. после закрытия обязательств отмена финализируется;
5. активные задачи прекращаются, доступные резервы освобождаются.

Это предотвращает исчезновение уже выданных материалов и оплаченных закупок из учёта.

## Роли

| Роль | Основная зона ответственности |
|---|---|
| `admin` | Полный доступ, пользователи и настройки |
| `manager` | Заявки, производство, закупки и общий контроль |
| `production_manager` | Производство, задачи, отмена заказов |
| `engineer` | База изделий, BOM и чек-листы |
| `warehouse` | Компоненты, резерв, выдача, приёмка и готовая продукция |
| `procurement` | Закупка дефицитных компонентов |
| `accounting` | Подтверждение оплаты |
| `assembler` | Получение комплекта и сборка экземпляров |
| `tester` | Чек-листы и решение «годно/дефект» |
| `repair_engineer` | Устранение дефектов и отчёт по экземплярам |
| `packer` | Упаковка прошедших тест изделий |
| `production` | Оперативное управление производством |

Пользователь может иметь несколько ролей. Backend проверяет роль на каждом защищённом API-маршруте.
